# Speed-ups the analyzer missed: pm-simfast, 2026-11-12

Source: predictionmojo `research/pm-simfast` (tests/simfast/PROFILE.md, RESULTS.md). The R95 market simulator went from 42.9 ms to
about 1 ms of CPU per swept configuration with byte-identical outputs; the head trainer gained a few percent. What produced the gain,
what this analyzer said about the 54943fa sources before the pass, and what it says now.

| speed-up (measured share of the 42.9 ms cell) | before | now |
|---|---|---|
| book walk: 9 scattered reads x 45 candidates x 1,702 nights, replaced by one gather into a table in walk order (53%) | MA113 on two inner indexings only | **MA151** scattered-gather on `frontier2.mojo:54`, `simreal.mojo:246/555`, `plateau.mojo:222`, `capsim.mojo:717` |
| picks, weights, per-pick prices recomputed for every cell although they depend on 9 of 35 knobs, one of which the grid varies (36%) | nothing | not detectable statically; MA151 points at the loops, the memo key is a design decision |
| `Sim.lab()` returns `self.grps[name].copy()`: 20 MB per cell (11.5%) | nothing | **MA150** copy-getter (medium when called from a loop) |
| 53 k small `List` allocations per cell from helpers that return a fresh list per night / row | MA301 on 8 same-function cases | **MA153** fresh-list-per-call on `tilt_w`, `skip_m`, `wvec_p`, `rec`, `rank`, `advrow` call sites |
| `s6().g`: a struct with two `String`s built per night for one Float64 | nothing | **MA152** temp-struct-field-in-loop |
| List bounds checks, 15.5% of samples | MA113 (28 findings) | unchanged; correct |
| headfast z row: 4 FMA accumulators -> 8, same bits | nothing | **MA154** fma-chain-width (low confidence: gain depends on the core's FMA latency and scheduler size) |

Things tried that the rules should not push:

- Replacing a 40-element sort + binary searches by an O(n^2) count of smaller / equal values (to drop the allocation) was 2x slower
  (5-8 ms per cell instead of 3). An insertion sort into a scratch buffer plus a walk over runs of equal values kept the exact ranks
  and removed the allocation. MA153's suggestion is "caller-owned buffer", not "avoid the sort".
- Vectorising a division-bound loop across lanes: on Haswell / Broadwell `vdivpd ymm` has the same per-element throughput as `divsd`,
  so MA102 / MA103 on loops whose body is 3 divisions and a square root per element promise a gain that the hardware does not give.
  A future rule could lower MA102's severity when the body is dominated by `/` and `sqrt`.
- A quantity test `Int(per / pc + 0.5) < 1` only needs the division when `pc > per`; a comparison first is exact. Too specific
  for a rule.

Rule ids start at MA150 so that they do not collide with MA138-MA143 of the unpublished 2026-11-11 round.
